category = CategorySerializer(read_only=True)
brand = BrandSerializer(read_only=True)

🔹 இதன் அர்த்தம்

--- ProductSerializer-ல் category & brand fields-ஐ nested serializer ஆக use பண்ணுறோம்.
--- read_only=True என்பதால் → client (POST/PUT) செய்யும்போது அதை அனுப்ப முடியாது.
--- But response (GET) பண்ணும்போது → nested details-ஆ return ஆகும்.

~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
🔹 Why read_only=True?

--- Client-ன் request-ல இப்படி full object அனுப்ப வேண்டிய அவசியம் இல்லாததால.
--- அதற்கு பதிலாக simple-ஆ category_id, brand_id (PrimaryKeyRelatedField) அனுப்பினால் போதும்.
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

--- category / brand → read-only → read செய்ய உதவும்
--- category_id / brand_id → write-only → create/update செய்ய உதவும்
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
✅ Simple line:
PrimaryKeyRelatedField use பண்ணுறதால foreign key field-க்கு client request-ல id மட்டும் அனுப்ப முடியும், nested object full-ஆ அனுப்ப வேண்டிய அவசியமில்லை.
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
🟢 மற்ற ways (just info)

--- PrimaryKeyRelatedField → id மட்டும்.
--- SlugRelatedField → name மாதிரி unique field கொண்டு identify பண்ணலாம்.
--- StringRelatedField → read-only; __str__() string மட்டும்.
--- HyperlinkedRelatedField → category-க்கு URL மட்டும் காட்டும்.

--- ஆனா practice-ல id (write) + nested (read) தான் easy & most used. ✅

✅ Summary:

--- Create/update easy → PrimaryKeyRelatedField.
--- Human-readable → SlugRelatedField.
--- Read-only text → StringRelatedField.
--- RESTful URL style → HyperlinkedRelatedField.
--- Detailed nested object → Nested Serializer.
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

🔹 source என்ன?

--- Serializer-ல நாம் declare பண்ணும் field name sometimes model-ல இருக்கும் field name-க்கு match ஆகாது.
--- அப்போ source use பண்ணி **“இந்த serializer field எதை model-ல link பண்ணணும்”**ன்னு சொல்லிக்கொடுப்போம்.

🔹 Example (உங்க codeல)

category_id = serializers.PrimaryKeyRelatedField(
    queryset=Category.objects.all(),
    source="category",   # Product model-ல actual field name
    write_only=True
)


--- Serializer-ல field name → category_id
--- Model-ல field name → category (ForeignKey)

👉 அதனால source="category" use பண்ணி mapping செய்கிறோம்.
👉 இதனால் request-ல category_id வந்தாலும், அது save ஆகும்போது Product.category-க்கு assign ஆகும்.
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
🔹 Breakdown (step by step)

1. category = CategorySerializer(read_only=True)

--- Response-ல் client category details full-ஆ பார்க்க உதவும்.
--- Create/update செய்ய client இதை அனுப்ப முடியாது (read_only).

2. category_id = PrimaryKeyRelatedField(...)

--- Request (create/update)-ல் client category id மட்டும் அனுப்ப முடியும்.
Example:

{ "category_id": 1 }

3. source="category"

--- Serializer-க்கு சொல்லுறது → "இந்த category_id value-ஐ எடுத்து, model-ல இருக்கும் category field-க்கு assign பண்ணு".
--- (Model-ல் category என்பது ForeignKey field தான்.)

4. write_only=True

--- இந்த field request-ல மட்டும் வேலை செய்யும் (write).
--- Response-ல திரும்பி காட்டாது (read முடியாது).
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

🔹 Final Understanding:

--- View/Read → category, brand (nested serializer).

--- Create/Update → category_id, brand_id (just ID மட்டும்).

--- PrimaryKeyRelatedField → ForeignKey relation-க்கு id கொண்டு instance set பண்ண.

--- source → அந்த id எந்த model field-க்கு save ஆகணும்னு mapping சொல்ல.

--- write_only → இது request-க்கு மட்டும், response-ல காட்டாதது.

🔹 GET

--- Normal read request.
--- Example: /products/ ku GET kudutha → products list kidaikum.

🔹 HEAD

--- GET maadhiri thaan, but response body varadhu.
--- Only headers return pannum.
--- Example:

GET /products/   → full data + headers
HEAD /products/  → only headers (Content-Type, Content-Length ...)

--- Purpose: Server-la data iruka? size enna? type enna? nu quick-ah check panna.
--- API clients/ browsers use pannum (time save panna).

🔹 OPTIONS

--- OPTIONS /products/ kudutha → server sollum:
--- indha endpoint ku ena methods allow pannuradhu (GET, POST, PUT …)
--- ena headers support pannuradhu.
--- Example response:

{
  "allow": ["GET", "POST", "OPTIONS"],
  "content-type": "application/json"
}


--- Browsers CORS preflight request la mostly OPTIONS use pannum.
--- i.e., unga frontend app (React, Angular, Vue) → API call pannum bodhu, first browser OPTIONS nu check pannum → "server accept pannutha?" nu paathu, appuram main request anuppum.

🔑 Why SAFE_METHODS la ivai mattum?

--- GET, HEAD, OPTIONS → data read/check panna only.
--- Data change pannaathu.
--- So safe methods nu solluvom.
--- Athanala permissions.SAFE_METHODS la include pannirukkanga.

👉 In short:

--- GET → Read data
--- HEAD → Headers only (faster check)
--- OPTIONS → Server info (allowed methods, headers etc.)

🔑 Summary

1. HEAD → use pannuvom:

--- big files download panna munnadi
--- links valid ah check panna
--- caching checks

2. OPTIONS → use pannuvom:

--- Browser CORS preflight (auto)
--- API testing (developer side)
--- Endpoint methods discover panna
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

🔹 SAFE_METHODS nu ennathu?

--- Django REST Framework la predefined constant:

permissions.SAFE_METHODS == ('GET', 'HEAD', 'OPTIONS')

--- Ithu data change pannatha methods.
👉 Meaning: read/check panna use pannuvom, modify panna use panna koodadhu.
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
if request.method in permissions.SAFE_METHODS:

🔹 request.method

--- Django REST Framework la, request.method = HTTP method (string).
--- Example values:
	* "GET"
	* "POST"
	* "PUT"
	* "DELETE"
	* "HEAD"
	* "OPTIONS"

🔹 permissions.SAFE_METHODS

--- Predefined constant in DRF.
--- Value = ('GET', 'HEAD', 'OPTIONS')
--- Ithu "safe methods" nu solluvom, because:
--- data change pannadhu
--- just read/check panna use pannuvom

🔹 Meaning of that line
if request.method in permissions.SAFE_METHODS:
→ Check pannudhu: current request method GET / HEAD / OPTIONS ah irukka?

✅ If yes → safe method → usually allow pannuvom.
❌ If no → (like POST/PUT/PATCH/DELETE) → adha next condition la check pannuvom (user role etc).

🔑 Summary

👉 Project run panna podhu:

--- DRF each request ku has_permission() method ku call pannum.
--- Safe methods (GET, HEAD, OPTIONS) → always pass.
--- Unsafe methods (POST, PUT, PATCH, DELETE) → only Admin/Seller pass.
--- Permission fail aa → DRF immediately 403 Forbidden return pannum.

BasePermission என்ன செய்கிறது?

--- எல்லா permission checks-க்கும் ஒரு common structure கொடுக்கிறது.
--- நீங்க custom rules எழுதணும்னா BasePermission inherit பண்ணிட்டு has_permission() அல்லது has_object_permission() method-ஐ override பண்ணலாம்.

Main Methods:

1. has_permission(self, request, view)

--- முழு request-க்கு permission check செய்ய பயன்படும்.
--- Example: ஒரு user login பண்ணியிருக்கிறானா இல்லையா, role என்ன, என்று check பண்ணலாம்.

2. has_object_permission(self, request, view, obj)

--- Individual object-level permission check செய்ய பயன்படும்.
--- Example: ஒரு user தனது சொந்த post-ஐ மட்டும் edit பண்ணணும், மற்றவருடையது அல்ல.

✅ Alternatives to BasePermission

1. Built-in Permission Classes (BasePermission-லிருந்து வந்தவை)

	** AllowAny → எல்லாருக்கும் access
	** IsAuthenticated → login ஆனவர்களுக்கு மட்டும்
	*** IsAdminUser → staff / admin-க்கு மட்டும்
	*** IsAuthenticatedOrReadOnly → login ஆனவர்களுக்கு full access, இல்லாதவர்களுக்கு read-only

2. get_permissions() Method Override

	** View/ ViewSet-குள்ள permission logic எழுதலாம், custom class இல்லாம:

class MyView(APIView):
    def get_permissions(self):
        if self.request.method == "GET":
            return [permissions.AllowAny()]
        return [permissions.IsAuthenticated()]

3. Django’s Built-in Auth System

	** @permission_required decorator
	** user.has_perm("app_name.permission_code")

if request.user.has_perm("blog.delete_post"):
    # do something

4. Queryset-based Restrictions

	** Permission logic queryset-லவே handle பண்ணலாம்:

class PostViewSet(viewsets.ModelViewSet):
    def get_queryset(self):
        user = self.request.user
        if user.is_staff:
            return Post.objects.all()
        return Post.objects.filter(owner=user)

5.Mixins

	*** Custom Mixin base class எழுதி, அதுல permission logic handle பண்ணலாம்:

class StaffOnlyMixin:
    def dispatch(self, request, *args, **kwargs):
        if not request.user.is_staff:
            return HttpResponseForbidden()
        return super().dispatch(request, *args, **kwargs)

6. Decorators for Function-based Views

	** @login_required
	** @user_passes_test(lambda u: u.is_staff)

1. DefaultRouter()

router = DefaultRouter()

--- Router என்பது DRF-ல் URLs auto-generate பண்ணுற ஒரு shortcut.
--- Normally, urls.pyல ஒவ்வொரு API viewக்கும் manually path() எழுத வேண்டி இருக்கும்.
--- ஆனா DefaultRouter use பண்ணினா, அது ViewSet methods (list, retrieve, create, update, destroy) அடிப்படையில் URL patterns-ஐ automaticா உருவாக்கும்.

2. router.register(...)

router.register('categories', CategoryViewSet, basename='categories')
router.register('brands', BrandViewSet, basename='brands')
router.register('products', ProductViewSet, basename='products')


register(prefix, viewset, basename) → மூன்று arguments:

	1. prefix → URL-ல பயன்படுத்தப்படும் ஆரம்ப prefix
		** 'categories' → /categories/
		** 'brands' → /brands/
		** 'products' → /products/

	2. viewset → எந்த ViewSet class அந்த prefix-க்கு map ஆகணும்னு சொல்லுது.
		** CategoryViewSet → categories-க்கு CRUD endpoints
		** BrandViewSet → brands-க்கு CRUD endpoints
		** ProductViewSet → products-க்கு CRUD endpoints

	3. basename → URL name prefix (reverse lookups, URL naming).
		** Example: basename='products' → URL name: "products-list", "products-detail"

✅ சுருக்கம்:

--- DefaultRouter → URLs auto-generate பண்ணும் tool.
--- register → எந்த ViewSet எந்த prefix-க்கு map ஆகணும்னு சொல்றது.
--- urlpatterns = router.urls → அந்த generated URLs-ஐ Django app-க்கு attach பண்ணுது.
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

📌 Reverse Lookups என்றால் என்ன?

1. Normal lookup → URL path-ஐ hardcode பண்ணி API-க்கு போவது.

url = "/products/1/"

2. Reverse lookup → URL name (ex: "products-detail") வைத்து Django/DRF URL-ஐ auto-generate பண்ணிடும்.
	👉 அதாவது, URL-ஐ hardcode செய்யாம, name use பண்ணி URL உருவாக்குறது.

📌 Example – DRF Router
	** நீங்க register பண்ணினீங்கன்னா:
		
router.register('products', ProductViewSet, basename='products')

	** இது இரண்டு முக்கிய URL names generate பண்ணும்:

"products-list" → /products/

"products-detail" → /products/{pk}/

📌 Why useful?

--- URL structure later change பண்ணினாலும் (ex: /items/ instead of /products/), name constant-ஆ இருந்தா எல்லாம் வேலை செய்யும்.
--- API responsesல hyperlinks கொடுக்கும்போது (HATEOAS style APIs), reverse lookup ரொம்ப useful.

✅ சுருக்கம்:
Reverse lookup = URL name use பண்ணி, actual URL auto-generate பண்ணுவது.

--- "products-list" → /products/
--- "products-detail" → /products/{id}/
