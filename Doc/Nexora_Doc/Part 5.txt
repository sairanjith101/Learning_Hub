1. Import statements

from rest_framework import permissions
from drf_yasg.views import get_schema_view
from drf_yasg import openapi

👉 permissions → DRF-ல் access control (who can see the Swagger docs).
👉 drf_yasg → Django REST Framework-க்கு Swagger / OpenAPI documentation generate பண்ணும் library.
👉 get_schema_view → Swagger / ReDoc UI-க்கு schema view generate பண்ணும் function.

2. openapi.Info(...)

👉 API-ஐ describe பண்ணும் metadata
👉 title → API name
👉 default_version → version number
👉 description → short info about project
👉 public=True → எல்லா users க்கு Swagger / ReDoc access கிடைக்கும்
👉 permission_classes=(permissions.AllowAny,) → Restriction இல்லாமல் public access

இதன் effect:

👉 swagger/ URL open பண்ணும் போது, API documentation browser-ல் show ஆகும்.
👉 ReDoc URL-க்கும் அது வேலை செய்கிறது.

👉 Rate limiting → ore user (ip address la irukura client) oru time frame la romba adhigama request panna stop panna.
👉 key='ip' → client IP address base panna limit apply pannum.
👉 rate='5/m' → oru IP ku 1 minute ku maximum 5 requests thaan allow.
👉 block=True → limit exceed aana udane request block pannum, response 429 Too Many Requests kudukkum.

Simple example

👉 Oru hacker/ bot register page ku 1 minute ku 100 request panna try panna,
👉 first 5 requests okay.
👉 6th request ku 429 Too Many Requests error varum.
👉 Ithu spam account creation ah prevent pannum, server overload ah avoid pannum.

Use case:

👉 Signup form, login form, password reset form la mostly use pannuvanga.
👉 DoS attack / brute force attack ku against safety.

👉 django-ratelimit ip based request speed ku limit set pannum. Ungal app la spam / abuse avoid panna use pannalam.

👉 Logging = program la nadakkura important events / errors ah record pannurathu.

Real life example:

👉 Train signal system la oru black box irukkum. Accident aana apuram, black box data pathi analyze pannuvanga → enna mistake, enna error nu purinjukkaradhuku.
👉 Software la logging file or console log → athu maari thaan.

Why we need logging?

👉 Debugging → Bug vandhaa, log file open pannitu reason kandupidikka easy.
👉 Monitoring → Production server la enna errors nadakuthu nu trace panna mudiyum.
👉 Audit trail → Yaar enna action pannanga, app epdi respond pannuchu nu record.

Logging Levels (importance order):

👉 DEBUG – developers ku deep info (backend la detailed steps).
👉 INFO – normal useful info (user created successfully, server started).
👉 WARNING – something suspicious, but app still working (disk space low).
👉 ERROR – app ku problem, request complete aagala (database connection fail).
👉 CRITICAL – severe error, app crash aagum danger.
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Django LOGGING dictionary la enna nadakuthu?

LOGGING = {
    'version': 1,
    'disable_existing_loggers': False,
    'handlers': {
        'file': {
            'level': 'ERROR',
            'class': 'logging.FileHandler',
            'filename': BASE_DIR / 'errors.log',
        },
    },
    'loggers': {
        'django': {
            'handlers': ['file'],
            'level': 'ERROR',
            'propagate': True,
        },
    },
}


Breakdown 🔎

1. 'version': 1
👉 Logging configuration system oda version (Python logging library la standard). Always 1 thaaan.

2. 'disable_existing_loggers': False
👉 Already Django/third-party use panra default loggers disable panna maaten nu solluthu.

3. Handlers section

'handlers': {
    'file': {
        'level': 'ERROR',
        'class': 'logging.FileHandler',
        'filename': BASE_DIR / 'errors.log',
    },
},

👉 handler = where to send the log messages.

file handler:

👉 level: 'ERROR' → Only ERROR and CRITICAL level messages log file ku write pannum. (INFO or WARNING varathu).
👉 class: 'logging.FileHandler' → Python logging la built-in handler, messages ah oru file ku write pannum.
👉 filename: BASE_DIR / 'errors.log' → log file path. BASE_DIR means project root directory. So log file → <project>/errors.log.

4. Loggers section

'loggers': {
    'django': {
        'handlers': ['file'],
        'level': 'ERROR',
        'propagate': True,
    },
},

👉 'django' → Django oda main logger (framework itself generate panna logs).
👉 handlers: ['file'] → All ERROR level logs from Django → file handler ku send pannum (i.e., errors.log la write pannum).
👉 level: 'ERROR' → This logger only accept ERROR and above messages.
👉 propagate: True → Log message ku parent loggers kum forward pannum (useful for combined logging).

Example 👇

👉 Suppose oru view la ZeroDivisionError throw aaguthu.
👉 Django log system detect pannum → log level = ERROR.
👉 Ungal configuration la ERROR messages file ku write pannum nu irukku.
👉 So → errors.log file la entry create aagum (with traceback).
